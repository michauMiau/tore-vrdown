# Teardown VR mod

A VR mod for Teardown. It is a DLL that gets injected into `teardown.exe`,
hooks the render path through vtable slots, and drives an OpenXR session that
acquires one image per eye and submits them per frame. No external overlay, no
ReShade, no Vorpx.

**The mod does not render in stereo yet.** Everything up to and including
acquiring both eye images works. `xrEndFrame` never returns, so the loop is
one call past the end. The sections below separate what was measured from what
was guessed, and this README is the current one; `docs/` is the journal that
got here, and its documents contradict each other wherever the understanding
changed. Where they disagree, the later dated one wins.

## Where it stands

**VERIFIED on the Windows test box, 2026-09-29** (`docs/DXGI_PRESENT_PIVOT_2026-09-29.md`)

```
xrCreateInstance       XR_SUCCESS
xrGetSystem            XR_SUCCESS
xrCreateSession        XR_SUCCESS   (device from the renderer's own swapchain)
xrBeginSession         XR_SUCCESS   READY -> SYNCHRONIZING -> VISIBLE -> FOCUSED
xrWaitFrame            XR_SUCCESS   shouldRender=1
xrBeginFrame           XR_SUCCESS
xrLocateSpace/Views    XR_SUCCESS   2 views, flags=0xf
xrAcquireSwapchainImage XR_SUCCESS  x2, idx=0
xrEndFrame             NEVER RETURNS
waits=1 ends=0 tracked=1 err=0
```

- A session is created and reaches FOCUSED. A full HMD pose is available.
- Both eye images are acquired. Per-eye acquisition is real, not simulated.
- `xrEndFrame` blocks, including when asked to end an empty frame. That points
  at the runtime's frame-completion path, not at layers, images or the copy.
  The open question is whether it is the runtime waiting on us or the runtime
  waiting on the game's outstanding Present.

**VERIFIED, live-tested 2026-09-27**

- A working `IDXGISwapChain::Present` hook, installed by writing vtable slot 9
  (`+0x48`). It counted 25 800 Present calls with the game alive.
- v53 was the first build stable across a long level: 12 840 frames, 3+
  minutes, no crash dialog.
- The `beginRender` and `endRender` vtable hooks are both per-frame and both
  receive the same renderer object.
- The build is clean of network capability. The injector imports only
  `KERNEL32.dll`, `msvcrt.dll` and `USER32.dll`. CI fails the build if a
  `ws2_32`/`winhttp`/`wininet` import ever appears.

**BLOCKED, and this is the whole remaining gap**

- `xrEndFrame` never returns. Until it does, nothing is submitted and nothing
  appears on the HMD.

**NOT STARTED**

- Stereo submission. Both images are acquired; neither is ever sent to the
  runtime, because the frame is never ended.
- Controllers and haptics. `lua/vrinput.lua` and `lua/vrhaptics.lua` map game
  events to OpenXR input, and the Lua suite exercises the mapping against a
  mock, but no controller path has been run against a live HMD.

**REFUTED, do not repeat these**

- Byte-stealing detours are safe. They are not. They killed builds v38 to v52
  with a delayed freeze and no dump. See ARCHITECTURE.md.
- `renderer+0xE40` is always the swapchain. It is the swapchain for the object
  `endRender` receives, and for no other object.
- `renderer+0x1130` is a ring of 0x40-byte matrix slots. It is not. The bytes
  there are pointers and ASCII, and a full memory scan found no matrix ring.
- The SceneDynamicBuffer is an `ID3D12Resource*`. It is a pointer to the
  engine's own abstract resource type, 24 bytes wide.

**A correction worth keeping.** An earlier revision of this README, and
`docs/OPENXR_2026-09-28.md`, reported the blocker as `xrCreateInstance`
returning `XR_ERROR_LIMIT_REACHED` (-10) on a Meta XR Simulator. That is
wrong twice over, and `docs/GRAPHICS_BINDING_2026-09-28.md` corrects it:
`xrCreateInstance` returns `XR_SUCCESS`; the failing call is `xrCreateSession`;
and the error is `-38` = `XR_ERROR_GRAPHICS_DEVICE_INVALID`, not `-10`. `-10`
was misread because `X->ResultToString` had never been bound to a real
instance, so every error printed numerically.

       ├─ hook layer        vtable patches, no byte stealing
       ├─ stereo layer      matrix math, verified offline
       └─ OpenXR layer      instance, session, frame loop

## Build

```sh
sh build.sh
```

Needs the mingw-w64 cross compiler, `x86_64-w64-mingw32-gcc`. On Debian or
Ubuntu, `apt install mingw-w64`. On Windows, MSYS2 with
`pacman -S mingw-w64-ucrt-x86_64-gcc`.

That produces `build/teardown_vr.dll` and `build/injector.exe`, strips them and
prints the injector's import table. The script passes `-I third_party`, because
`hook/xr_session.h` includes `<openxr/openxr.h>` and the headers are vendored
there. Without that flag the build fails with
`fatal error: openxr/openxr.h: No such file or directory`.

There are no `-fexceptions` flags, on purpose. mingw's `excpt.h` defines
`__try1` and `__except1` but not `__try` and `__except`, and gcc 14 posix has no
`-fseh-exceptions`, so no flag combination makes SEH compile here. Reads of
game memory go through `ReadProcessMemory` on our own process instead, which
probes the range in the kernel and returns a short read rather than raising.

## Test

```sh
sh tests/run_tests.sh     # five offline C unit tests, native gcc
cd lua && sh run_tests.sh # syntax check, rebuild merged build, two suites
```

Both run in CI on every push, along with the cross-build and the PE checks, so
a green check means the tree still compiles and the unit tests still pass. The
runtime behaviour above is not covered by CI: it needs the Windows box and a
live HMD.

| Test | What it pins down |
|---|---|
| `tests/test_present_patch` | the Present install path, under AddressSanitizer |
| `tests/test_memscan` | the SceneDynamicBuffer shape test, 20 000 random blocks, 0 false positives |
| `tests/test_detour` | trampoline back-jump layout, and the old offset-8 regression |
| `tests/test_atomic` | the atomic publish, 0 torn reads |
| `tests/test_stealable` | the prologue length measurer refuses what it cannot decode |

`test_detour` and `test_stealable` still pass even though byte-stealing is
banned. They guard code that is compiled in but not installed.

The Lua suite checks every file parses, rebuilds the single-file variant and
runs it twice: once modular, once with `dofile()` hard-disabled, because the
merged build is the fallback path for when the game refuses a multi-file mod.

## Run

See BUILD_AND_RUN.md for the full procedure. The short version: SSH gives you
session 0, which has a different window station, so anything that needs to see
windows or take a screenshot has to run as an interactive scheduled task.

```powershell
# from SSH, session 0
.\tools\ps\run_in_session1.ps1 -Script C:\tdvr\full_run.ps1 -WaitSeconds 300
```

Defender will flag the injector. That is expected; `docs/DEFENDER.md` explains
why.

## CI

`.github/workflows/build.yml`, on every push and pull request:

1. installs mingw-w64 and Lua 5.1,
2. runs `build.sh` and checks both artifacts exist, are over 1 KB, and are
   64-bit PE (`PE32+` / `x86-64`),
3. fails on any network DLL import in either binary,
4. runs the C unit tests and the Lua suite,
5. uploads both binaries as artifacts.

## Two measurements that will bite you

**A process check does not mean the game is alive.** A frozen game keeps its
pid and still answers `Responding`. A live renderer burns CPU and a frozen one
does not, so a flat CPU counter means the opposite of healthy. Use
`tools/ps/monitor_run.ps1`, which watches screen pixels and CPU together.

**The game sits on a legal warning screen until somebody presses a key.** Until
that happens it renders nothing, and a run that never pressed the key proves
nothing at all.
