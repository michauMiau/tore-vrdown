# Teardown — controller input scheme and binding model

**Date:** 2026-09-27
**Purpose:** a concrete, implementable action→binding table so the VR mod can drive the game.

Every claim is tagged **VERIFIED** (bytes read, or shipped file read, with the disassembly quoted)
or **UNVERIFIED**. This project has burned 60+ builds on inferred offsets, so the distinction is the
substance of this document, not a closing disclaimer.

Two facts dominate the design:

1. The binding scheme is **declarative, shipped as XML, and parsed at runtime** — not hardcoded.
   `data/input_settings.xml` fully defines action→button mapping per mode.
2. **teardown.exe imports no controller API at all.** It reads pads through Steamworks
   `ISteamInput` obtained from `steam_api64.dll`. No XInput, HID, DirectInput, GameInput or SDL.
   A virtual `xinput1_4.dll` will do nothing.

---

## 1. The scheme is a data file (VERIFIED)

**`data/input_settings.xml`**, 10,336 bytes, the shipped default. Confirmed byte-identical on the
live install: `sha256 4818365b4cccb9a141c89653af82aacbf8ac1b8ba4b67f2658c9b4dffe9d95ea`, with
`LastWriteTime == CreationTime`, so it has never been rewritten.

The string `data/input_settings.xml` sits at **RVA 0x009DF378**, referenced from a 7-function parser
cluster spanning **0x0018B4E0 – 0x0018D174** (bounds read from the `.pdata` unwind table; entries
are 12 bytes — `begin_rva`, `end_rva`, `unwind_rva`, little-endian `uint32`).

```
<input_settings>
  <system>      virtual_mouse_sensitivity, device_enumeration_interval
  <mouse>       sensitivity, zoom_sensitivity, <bindings>
  <keyboard>    <action name=... key=.../>          (flat, no <bindings> wrapper)
  <gamepad>     sensitivity params, then <bindings><mode name="..."> per mode
  <sensitivity> response <curve> definitions
</input_settings>
```

Element forms: `<action>`, `<button name= action=>`, and `<shortcut button1= button2= action=>`.
`toggleable="true"` is honoured and used exactly once in the defaults (`gamepad_button_b` → `crouch`).

**Modes:** `none` (empty, reserved for global shortcuts), **`menu`**, **`player`**, **`driving`**.
`player` and `driving` are mutually exclusive game states, so any remap must be mode-aware.

## 2. The action enum — 51 entries, VERIFIED

**Table base RVA 0x009DEB58** (file 0x9DD758), `.rdata`, **16-byte stride**, layout
`{ const char* name; uint32 id; uint32 pad; }`, **51 entries, index 0…50**.

The enum value is the **array index**, not the stored `+8` field. Three independent proofs:

* Bounds check, disassembled from the file (`pefile.py fn 0x0018A260`):
  ```
  0018A269: 80 fa 33              cmp dl, 0x33        ; id < 51 ?
  0018A26C: 73 1f                 jae 0x18a28d        ;   else -> fallback
  0018A26E: 0f b6 d2              movzx edx, dl
  0018A271: 48 8d 05 e0 48 85 00  lea rax, [rip + 0x8548e0]   ; -> 0x009DEB58
  0018A278: 48 03 d2              add rdx, rdx
  0018A27b: 48 8b 14 d0           mov rdx, qword ptr [rax + rdx*8]
  ```
  `rdx*8` from a 16-byte stride, doubled by `add rdx,rdx`, loads only the name pointer at +0.
  `0x33` = 51 = the entry count.
* Entry 50's `+8` field is `1952867692` = `0x7466656C` = ASCII `flet` — a pool fragment, not an id.
* The Steam Input hot path writes index immediates that match the table: `mov byte ptr [rbp-0x10], 5`
  next to the string `flashlight` (index 5), then 6 `interact`, 7 `jump`, 8 `crouch`.

Regenerated by `teardown-analysis/table_extent.py`, which walks until the first qword stops being a
valid image pointer and then checks for duplicate pointers. It stops at index 51, where the qword is
`0x0000007468676972` = ASCII `righ` (pool bleeding in, which proves the boundary), and reports
**51 distinct name pointers, no repeats**.

## 3. Button and axis identifiers (VERIFIED)

Button/axis identifier strings live in `.rdata` at **0x00A51690 – 0x00A519BB** as inline ASCII:
`gamepad_dpad_left/right/up/down`, `gamepad_button_b/a/y/x`, `gamepad_button_l1/l2/l3`, `r1/r2/r3`,
`back`, `menu`, `share`, `gamepad_left_stick` + `_x/_y/_left/_right/_up/_down`,
`gamepad_right_stick` + `_x/_y/_left/_right/_up/_down`, `gamepad_dpad_leftright`, `gamepad_dpad_updown`.

They are reached through a pointer array at file **0xA4FFF8**, entries 16 bytes apart (0xA4FFF8,
0xA50008, 0xA50018, …, one per button, pointer at +0). No direct rip-relative reference from `.text`
into the string block exists — the pointer array is the only confirmed route in. **The array's base
RVA and its per-entry meaning are UNVERIFIED**; only the pointer values are confirmed.

Device families the game recognises, each resolved from a rip-ref and read as a string:
`gamepad_ds4`, `gamepad_ds5`, `gamepad_xbox`, `gamepad_xbox360`, `steam_controller`,
`steamdeck_controller`, `generic_gamepad`.

Action index 0, `none`, is deliberately absent: it is the sentinel the engine uses for "no binding"
(the `none` mode block in the XML is the empty placeholder), not an action anything can bind to. So
51 enum entries − `none` = the 50 rows above, which matches the action names actually appearing in
`input_settings.xml`. Cross-checked programmatically: every `(name, index)` pair in this table
matches the binary-derived enum, with zero mismatches and zero duplicates.

Notes, each tied to the file:

* **Mode collision:** physical R2 is `lmb` in `menu` but `usetool` in `player`; L2 is `rmb` in menu,
  `grab` in player, `down` in driving. A VR remap must be mode-aware.
* `crouch` is the only `toggleable="true"` default: a press latches until pressed again. The engine
  honours the attribute (parser compares `"toggleable"`, RVA 0x009DF290), so a mod can set it on any
  action.
* `left/right/up/down` in `menu`/`player` are **stick direction pseudo-buttons**
  (`gamepad_right_stick_left` etc.), not analog reads. Driving mode has no stick directions —
  steering there is the raw `camerax`/`cameray` pair.
* `usetool`/`grab` sit on **analog triggers**. Deadzones from the file: sticks inner **0.12** /
  outer **0.0**, triggers inner **0.05** / outer **0.0**. These four are the only deadzones the
  game reads.
* `<sensitivity><curve>` defines 16 curves; `linear` is the `leftStick` default, `quadratic` the
  `rightStick` default. The other 14 (incl. `magnetism_*`, `friction_*`, `input_mapping_dual_zone`)
  ship unused and are available for tuning. Their intended target is **UNVERIFIED inference**.

## 5. Where a VR mod should inject

**VERIFIED — the game imports no controller API.** Import directory at RVA 0x00BED614 (DD[1] size
0x2A8 = 34 × 20 bytes). All 33 descriptors and every thunk walked: `sentry`, `mimalloc`, `WSOCK32`,
`WS2_32`, `OPENGL32`, `dxgi`, `dbghelp`, `amd_ags_x64`, `KERNEL32`, `USER32`, `GDI32`, `ADVAPI32`,
`SHELL32`, `ole32`, `OLEAUT32`, `MSVCP140`, `IMM32`, **`steam_api64`**, `DSOUND`, `bcrypt`,
`VCRUNTIME140`, `VCRUNTIME140_1`, and 11 `api-ms-win-crt-*`. No `xinput*`, `hid`, `dinput`,
`setupapi`, `sdl` or `GameInput` — and no such string anywhere in the 30 MB image.

**VERIFIED — it reads pads through `ISteamInput`.** Function 0x004DA940–0x004DA967 (39 bytes, from
`.pdata`), disassembled from the file:

```
004DA940: 40 53                 push rbx
004DA942: 48 83 ec 20           sub rsp, 0x20
004DA946: 48 8b d9              mov rbx, rcx
004DA949: ff 15 59 88 4a 00     call qword ptr [rip + 0x4a8859]   ; IAT 0x009831A8
004DA94f: 8b c8                 mov ecx, eax
004DA951: 48 8d 15 58 0d 57 00  lea rdx, [rip + 0x570d58]         ; -> 0x00A4B6B0
004DA958: ff 15 5a 88 4a 00     call qword ptr [rip + 0x4a885a]   ; IAT 0x009831B8
004DA95e: 48 89 03              mov qword ptr [rbx], rax
004DA961: 48 83 c4 20           add rsp, 0x20
004DA965: 5b                    pop rbx
004DA966: c3                    ret
```

The `lea` bytes `48 8d 15 58 0d 57 00` give disp32 `0x570D58`; `0x4DA958 + 0x570D58 = 0x00A4B6B0`,
whose 14 bytes are `53 74 65 61 6d 49 6e 70 75 74 30 30 36 00` = `"SteamInput006"`. IAT slot
0x009831A8 decodes to `steam_api64.dll!SteamAPI_GetHSteamUser`, 0x009831B8 to
`SteamInternal_FindOrCreateUserInterface`, both read from the import descriptor.

The per-action read loop, from the 2688-byte function at 0x004DD2F0, repeated once per action:

```
004DD30a: 48 8d 0d f7 b0 76 00  lea rcx, [rip + 0x76b0f7]   ; -> 0x00C48408 (accessor slot)
004DD311: ff 15 99 5e 4a 00     call qword ptr [rip + 0x4a5e99]
004DD317: 48 8d 15 82 1b 50 00  lea rdx, [rip + 0x501b82]   ; -> 0x009DEEA0 "flashlight"
004DD31e: 48 8b 08              mov rcx, qword ptr [rax]
004DD321: 48 8b 01              mov rax, qword ptr [rcx]     ; interface vtable
004DD324: ff 90 80 00 00 00     call qword ptr [rax + 0x80]  ; Steam Input vtable slot
004DD32a: 4c 8d 45 10           lea r8, [rbp + 0x10]
004DD32e: c6 45 f0 05           mov byte ptr [rbp - 0x10], 5 ; action index 5
```

Both `lea` targets were recomputed from the instruction bytes and land where claimed.

**UNVERIFIED:** which `ISteamInput` method is vtable slot 0x80 (the 17th virtual, consistent with
`GetDigitalActionOrigins`). The vtable layout of the Steam Input build in use is not in this binary.
Do not hardcode a method name on this.

**VERIFIED — Raw Input is mouse-only.** The single `RegisterRawInputDevices` call (0x4F2689) writes
`mov qword ptr [rbp+0x10], 0x20001` — usUsagePage 0x02 (HID generic) / usUsage 0x01 (mouse),
`dwNumDevices = 1`. A pad would be page 0x01 usage 0x04/0x05. Both `GetRawInputData` sites
(0x4F0356, 0x4F038A) test `cmp dword ptr [rsp+0x60], 0` and discard anything not `RIM_TYPEMOUSE`.

**VERIFIED — the live VM has no input DLLs to conflict.** `xinput1_4/1_3/9_1_0/1_2.dll`,
`dinput8.dll`, `hid.dll`, `SDL2.dll`, `GameInput.dll`, `openvr_api.dll` are all absent from the game
folder and a recursive sweep. `steam_api64.dll` is the genuine 298,384-byte Valve build
(version 07.40.51.27) with no `.orig`/`.bak` beside it. No physical controller or VR HMD is
attached.

> **Caveat on the local decrypted copy:** `/root/steamless/Teardown/steam_api64.dll` is
> **7,305,128 bytes** and contains `VR_Init`, `VR_GetGenericInterface`, `VR_IsHmdPresent` and the
> full `SteamAPI_ISteamInput_*` export list — it is a **Steam API proxy with OpenVR forwarding**,
> not Valve's DLL. A real 298,384-byte `steam_api64.dll.orig` sits beside it. The live VM does not
> have this proxy. Local static analysis is reading the proxy, not the game.

### Recommended injection point — three rungs, best first

1. **Lua, in-mod (VERIFIED, works today, no patching).** The game exposes `InputDown`, `InputPressed`,
   `InputReleased`, `InputValue`, `InputClear`, `InputResetOnTransition`, `LastInputDevice`,
   `DisablePlayerInput` to mods. All present as strings in the binary — `InputPressed` 0x00A41BA0,
   `InputDown` 0x00A41BC8, `InputValue` 0x00A41BD8, `InputClear` 0x00A41C60, `LastInputDevice`
   0x00A41C88 — and documented in `data/script_defs.luau` with signatures. The game's own UI calls
   them on exactly the names in §4: `ui/map.lua` uses `InputPressed("interact")`,
   `InputPressed("mmb")`, `InputDown("menu_left")`; `ui/ui_common.lua` uses
   `InputValue("up") - InputValue("down")`. A mod can therefore poll every action by name, and
   `InputClear()` lets it hide input it consumed. **Cheapest correct path; needs no offset.**
2. **Rewrite the binding data.** The scheme is XML parsed at runtime, so a mod can supply its own
   bindings — but per-user bindings actually live in
   `C:\Users\vm\AppData\Local\Teardown\options.xml` (6,468 B), which encodes them as
   `value="<action> <toggleable> <?>"` triplets, e.g. `gamepad_button_b value="crouch 1 0"`.
   Writing that file is a **user-data change, not a patch**, and the mod must not clobber user edits.
3. **Hook the engine's state read.** The repeated loop at 0x004DD30A is where Steam Input handles
   become per-action state. Overwriting the result there is the surgical option and the only one that
   survives an XML change. 0x004DA940 (interface accessor) is the other probe point.

**Haptics** are covered in `docs/HAPTICS_FOUND.md`: 57 declarative `data/haptic/*.xml` files
(`keypoints`/`motor`/`adaptive_trigger`/`advanced_vibration`) parsed by the cluster at 0x001A7A90 /
0x001A7C00. The engine's only output is a Steam Input call, so that is where playback interception
belongs.

`InputValue("…")`, and the defaults are a shipped XML file. Only rung 3 needs a hook, and
0x004DD30A plus the 0x004DA940 accessor are the two places worth probing first.
